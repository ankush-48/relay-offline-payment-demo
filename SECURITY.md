# Security notes

Relay is an educational simulator, not a production financial service. Packet encryption uses RSA-OAEP and AES-GCM; ingestion checks packet age; and settlement checks the simulated balance. Nothing connects to UPI, a bank, or real funds.

The hosted public demo creates a separate temporary workspace for each HTTP browser session. Each workspace has distinct demo accounts, transactions, and a virtual mesh. Account and transaction endpoints are scoped to that workspace, public writes are rate-limited, each transfer is capped at ₹500, and public callers cannot reset the mesh or call the bridge ingestion endpoint directly. Inactive workspaces expire and their demo records are removed. Session workspaces are temporary and do not survive service restarts.

Responses under `/api/` are marked `Cache-Control: no-store` to prevent browser or shared proxy caching of session-scoped data. The app also sends a restrictive Content Security Policy, anti-framing and content-sniffing headers, and HSTS when served through the HTTPS Render proxy. Inline scripts and styles remain enabled because the current dashboard is a single Thymeleaf template; extracting them into versioned static assets would allow a stricter script policy.

Public workspace entry asks for a display name only. It does not verify a real identity or deliver Gmail/SMS OTPs. The local OTP flow is also a demo and returns the generated code to the local UI; do not present it as real contact verification. Workspace isolation is session-based rather than a persistent user account: clearing cookies, changing browser profiles, or allowing someone to use the same browser session can change who can access that workspace. A production login would require a configured identity provider and provider credentials.

Browser offline queue data is stored locally and is not secure wallet storage. The hosted H2 database, in-memory sessions, packet keys and idempotency state are demonstration choices and may reset. Do not use this project to initiate or claim a real payment. A production financial product would need a dedicated authentication and authorization design, persistent managed storage, protected signing keys, audited bridge credentials, monitoring, and independent security review.
